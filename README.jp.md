# find-unknowns

自分のタスクについて「自分が何を分かっていないか」を、実装の前、最中、後に見つけるための Claude Code スキルです。

## このスキルがやること

依頼したとおりに作ってもらったのに、できあがったものは望んだものと違っていた。そういう経験は、指示の書き方が下手だったせいとは限りません。依頼した内容と、実際の作業が要求するものとのあいだには、依頼者自身がまだ気づいていないギャップ（**未知**、unknowns）があります。エージェンティックコーディングの品質は、この未知に上限を決められます。

自分で気づけないものを、自分で埋めることはできません。そこでこのスキルは、Claude をファシリテーターにします。いまボトルネックになっている未知がどの種類かを診断し、それに合った発見パターンを Claude のほうから実行します。

| あなたの状況                                                 | Claude が実行するパターン                                                                          |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| ドメインやコードベースのその部分に不慣れ                     | **ブラインドスポットパス**：先に現場を調査し、「聞くべきだったのに知らなかったこと」を教えてくれる |
| 「見れば分かるんだけど言葉にできない」、またはスコープ未確定 | **ブレインストーム＆プロトタイプ**：安価なモック3〜5個、または安い順の1行案5〜10個に反応してもらう |
| 仕様はあるが、聞かれれば答えられる空白がある                 | **インタビュー**：一度にひとつずつ、アーキテクチャを左右する質問から                               |
| 言葉にできないが、参考になる実例がある                       | **リファレンス**：実例を読み込み、転用できる本質を抽出する                                         |
| 実装を始める準備ができた                                     | **実装計画**：決めるべきことを先頭に、機械的な作業は最後に                                         |
| 実装の真っ最中                                               | **実装ノート**：計画からの逸脱をすべて `implementation-notes.md` に記録し続ける                    |
| 完成後、関係者の承認が必要                                   | **ピッチ／説明資料**：判断の経緯をレビュアー向けにひとつの資料へ                                   |
| 完成後、マージする直前                                       | **クイズ**：変更内容の理解度クイズ。合格してからサインオフ                                         |

表の上から五つは実装前、六つめは実装中、残りの二つは実装後に当たります。同じ「分かっていない」でも、段階ごとに正体が違う、ということです。

ファシリテーターといっても、質問攻めにはしません。1ターンに必須の質問はひとつだけです。提示する論点は最大でも3〜5個で、残りは保留して、必要なら出せると伝えるにとどめます。穴埋めテンプレートは、頼まれない限り出しません。また、依頼文から読み取った出発点を最初に復唱します。読み違いがあっても、そこで訂正できれば、まだ何も失っていません。そして毎回、すぐに行動へ移せる成果物で締めくくります。多くの場合それは、元の依頼文を研ぎ直したプロンプトです。

## スキルの構成

八つのパターンを一つのスキルに詰めると、Claude が毎回読む量が膨らみそうに思えます。実際に読むのは、ルーターと、選んだパターンのリファレンス一つだけです。

```text
find-unknowns/
├── SKILL.md        # 決定的な6ステップのルーター：非適用判定 → 段階（ライフサイクル）判定 →
│                   # パターン選択（最初に一致した規則が勝つ） → 参照読込 →
│                   # 実行（数えられるガードレール） → 二値の自己チェック
├── references/     # 1パターン1ファイル。Claude は選んだ1ファイルだけを読む
│                   # （各ファイル：適用条件、入力、手順、初回契約、成果物、
│                   #   停止条件、良い例／悪い例の対照、二値の自己チェック）
└── assets/
    └── implementation-notes-template.md   # 実装ノートパターンが、あなたのリポジトリへコピーする
```

ルーターと各リファレンスは、上限を「数えられる」形で書いています（必須質問は1つ、提示する論点は3〜5個、抽出する性質は3〜7個、クイズは4〜7問、といった具合です）。「ほどほどに」「必要なら」のような程度表現は、モデルごとに解釈が揺れます。数なら揺れません。だから、フロンティアモデルでなくても、同じ規律でこのスキルを実行できます。

## 使いどころ

- 大きい、曖昧、仕様が固まっていないタスク（「アプリに通知機能つけて」など）
- 触ったことのないドメイン、ライブラリ、コードベースの領域での作業
- 選択肢を見て初めて好みが分かる、センスが問われる作業
- 自分で一行ずつ書いたわけではない大きな変更をマージする前

どれも、自分が何を知らないかを自分では言えない状態です。

## 使わないほうがよい場面

- タスクがすでに完全に仕様化されている。そのまま実装すればよい
- 合意済みの仕様があり、決定を蒸し返してほしくない
- 定型作業。原因の明確なエラーのデバッグ、リネーム、小さく範囲の明確な修正

こちらは、分かっていないことがもう残っていないか、残っていても今は決めたくない状態です。割り込む価値がありません。

## 使い方

明示的に呼び出すのが確実です。

> 「始める前に**ブラインドスポットパス**をやって。認証まわりのコードは触ったことがないんだ」
> 「作り始める前に、この機能について**インタビューして**」
> 「マージする前に、この変更について**クイズを出して**」

**自動発動についての注意：** このスキルの説明文（トリガー条件）は、意図的に控えめに調整してあります。仕様が明らかに曖昧な依頼では自動的に発動することもありますが、実装する準備ができている人の邪魔だけはしない、という設計です。発動率よりも誤発動ゼロのほうを優先しました。特定のプロジェクトで積極的に発動させたい場合は、そのプロジェクトの `CLAUDE.md` に一行足してください。例：_「依頼が曖昧なときは find-unknowns スキルを使うこと」_

## 検証について

軽くしたぶん、効き目まで軽くなっていないか。それを確かめるために、ベンチマークを回しています。

このスキルは、8つの採点付きシナリオ（ブラインドスポットパス、デザイン方向性、曖昧な機能依頼、実装中の計画逸脱、マージ前クイズ、リファレンス探索、実装計画、ピッチ）からなるベンチマークスイートに対して、スキルの有無とモデルの両方をまたいで比較しながら開発しました。直近のマトリクス（Claude Fable 5 と Claude Sonnet 5 のそれぞれで、旧版と現行版を実行）では、現行版が両モデルとも 41/41 のアサーションに合格しています。旧版は、ルーティングの曖昧さで3件を落としていました。現行版はそこを解消し、Sonnet を Fable と同等の品質まで引き上げています。評価の定義とフィクスチャは [`evals/`](evals/) にあり、実行も拡張もできます。

ただし、この数字はフィクスチャの上での話です。冒頭の、できあがってから違うと気づく場面がどれだけ減るかは、自分のリポジトリで走らせてみるまで分かりません。
