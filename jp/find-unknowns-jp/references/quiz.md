# クイズ（実装後）

長いセッションの後では、diff は変更の実態を過小に伝える。挙動は diff に映らない既存のコードパスに依存しているからだ。何をなぜ行ったかの文脈と直観が掴めるレポートを渡し、そのうえでクイズを出す。ユーザーに繰り返し伝える価値のある基準：**合格するまでマージしないこと。**

## 適用条件

- 作業（あなた、同僚、または過去セッションによる）が完成し、ユーザーがマージや引き継ぎの前に本当に理解する必要がある。
- ユーザーが「この変更についてクイズを出して」「ちゃんと理解できているか確かめたい」と言った。
- 変更の挙動が diff の外のコードパスに依存している——まさに、diff だけを読むと偽の自信が生まれる状況。

読み手が「納得させるべき他者」ならピッチ／説明資料を。検証なしの要約だけ欲しいなら、レポートを渡してクイズを提案する——ただし、その提案が何を防ぐためのものかを言うこと。

## 手順

1. **diff ではなくソースを読む。** 変更されたコードが何を呼び、何から呼ばれるかをたどる。ファイルをスタブ化・省略した diff は、クイズが扱うべき挙動をまさに隠している。渡された diff と実ソースが食い違ったら、ソースが正であり——その食い違い自体がクイズの素材だ。
2. 変更の本当のリスク面を探す：エラーパス、フォールバック、再起動を生き延びない状態、既存の呼び出し元への静かな挙動変更。
3. 先にレポートを書く：文脈（なぜこの変更が存在するか）、直観（システムの既存概念の言葉で、どう動くか）、何をしたか、何に注意すべきか。クイズが機能するのは、レポートを読めば合格し得る場合だけだ。
4. クイズを4〜7問、**トリビアではなく挙動について**書く——鋭いレビュアーが聞く質問。「ワーカーがジョブの途中で再起動したらリファンドはどうなる？」は「新しいモジュールの名前は？」に勝る。少なくとも1問は答えが diff の外にあるもの、1問は失敗パスに関するものを入れる。
5. ユーザーの解答を正直に採点する。外した箇所はコードを指し示して説明し、合格するまで変化形を出し直す。念を押すこと：合格前のマージは、チームの誰も理解していないコードのマージだ。

## 出力契約

成果物ひとつ（チャットメッセージまたは HTML/markdown レポート、ユーザーの求めに応じて）を次の形で：

1. **文脈** — この変更がどの問題を解くのか、数文で。
2. **直観** — システムの既存挙動と接続した動作原理。diff 外のコードパスはここで説明する。
3. **何をしたか** — 具体的な変更、簡潔に。ファイルは貼らずにリンクする。
4. **クイズ** — 挙動に焦点を当てた4〜7問。答えは伏せる。
5. 締めの基準：解答は採点され、合格するまでマージしないことを推奨する。

## 良い例／悪い例

**良い例**（非同期リファンド変更へのクイズ2問）：

> 3. リファンドジョブがワーカーに拾われ、決済プロバイダの呼び出しは成功したが、DB 書き込みの前にプロセスがクラッシュした。顧客がリトライする。**二重にリファンドされるか？ 理由も含めて説明せよ。**
> 4. `recent-change.diff` では `queue.js` がスタブになっている。実ソースでは、**バリデーションに失敗したジョブはどうなり——誰がそれを知るか？**（ヒント：catch ブロックがジョブをどうしているか見よ。）

**悪い例**（同じ変更）：

> 3. 追加された新しいファイルの名前は？
> 4. ○か×か：リファンドエンドポイントは HTTP 202 を返すようになった。
> 5. キューは何回リトライを試みるか？

悪い例はトリビアだ——diff を流し読みすれば答えられ、理解せずに暗記でき、どの問いも本物の地雷（バリデーション失敗ジョブが静かに落ちる）を捕まえない。ユーザーは満点を取ってなお、説明できないサイレント・デッドレターのバグをマージし得る。

## 送信前の自己点検

- 変更が触れる実ソースを読んだか？ diff だけではないか？ diff がファイルをスタブ化しているなら、その裏を取ったか？
- すべての問いは**挙動**についてか——レビュアーの障害ポストモーテムの質問と置き換え可能か？ 名前を grep すれば答えられる問いは削る。
- 少なくとも1問は diff の外の知識を要求し、1問は失敗パスを扱っているか？
- レポートを読めばユーザーは合格し得るか——そして合格は本当に理解を保証するか？
- 「合格するまでマージしない」の基準を明言したか？
