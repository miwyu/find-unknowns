# 実装計画

計画は「徹底ぶりの証明」ではなく「論点の顕在化」のために書く。計画の主役はレビューするユーザーだ。ユーザーの入力が意味を持つ場所に注意が向くよう並べること。

## 適用条件

- 発見フェーズが終わり（またはそもそも不要で）、ユーザーは実装準備完了だが、コードを書く前に論点を洗い出したい。
- 残った曖昧さがアーキテクチャを変えない——変えるなら先にインタビュー。計画は発見の出口であって入口ではない。
- ユーザーが計画、あるいは「始める前に何をレビューすべきか」を求めた。

## 手順

1. 入力を集める：確認済みの仕様、プロトタイプやリファレンス、ブラインドスポットパスやインタビューで浮かんだもの。計画が触れるコードを読む。
2. 計画を**レビューでユーザーが変えそうな順**に並べる：データモデルの変更、新しい型インターフェース、ユーザーに見えるものすべてを先頭に。機械的なリファクタリングは末尾へ（「そこは任せる」ゾーン）。
3. 決定を含む項目ごとに、下した決定と却下した代替案を各1行で示す——ユーザーは見えるものにしか拒否権を行使できない。
4. 実装中にしか解けない未知を明示し、作り手がどう扱うべきかを書く（ここで実装ノートパターンの準備が整う）。
5. 実装は**新しいセッション**で、計画とプロトタイプを成果物として渡して始めることを提案する。作り手はクリーンなコンテキストと、計画フェーズで掘り出したすべてを両方手にできる。

## 出力契約

計画文書ひとつ（チャットに markdown、求められればファイル）を次の形で：

1. **レビューしてほしい決定** — 変わる可能性が最も高い3〜5項目：データモデル、インターフェース、ユーザーに見える挙動。各項目：何を選んだか、何を却下したか、なぜか。
2. **順序** — 構築の順番、簡潔に。
3. **機械的な作業** — リファクタリングと配管。末尾に数行へ圧縮。
4. **残存する既知の未知** — 構築中にしか現れないものと、実装ノートを保持せよという指示（`assets/implementation-notes-template.md` を指す）。
5. 締めに、この計画を成果物として新セッションで実装する提案。

計画はレビューのためのもので、保管のためのものではない。ユーザーが読み飛ばしそうなセクションは削る。

## 良い例／悪い例

**良い例**（計画の冒頭）：

> **レビューしてほしい決定**（あなたの目で変わる可能性が高い順）：
>
> 1. **新テーブル `refund_jobs`**。`payments` にステータス列を足す案ではなく——支払い行を不変に保てる。却下案：ステータス列方式。安いが監査クエリが汚れる。
> 2. **冪等性キーはクライアント支給ヘッダー**、必須。却下案：サーバー生成フォールバック——リトライのセマンティクスを静かに壊す。
> 3. **webhook 消費者に見せるのは `refund.settled` のみ**。中間状態は外に出さない。却下案：全状態ストリーム。誰も求めていない。
>
> 順序：マイグレーション → ジョブランナー → API → webhook。機械的作業：`validateAmount` ヘルパー抽出、死んだフラグ2本の除去（文書末尾）。

**悪い例**（計画の冒頭）：

> ## フェーズ1：準備
> 1.1 フィーチャーブランチを作成。 1.2 既存コードをレビュー。 1.3 テストフィクスチャを用意。
> ## フェーズ2：実装
> 2.1 モデルを更新… [時系列順の番号付きステップが40個続き、データモデルの決定はステップ2.3に「必要に応じてスキーマを更新」とだけ書かれて埋まっている]

悪い例は実行の時系列で並んでいるため、レビュー可能な決定がリストの中程に埋まり、選択ではなくタスクとして表現されている。ユーザーは拒否権を行使できるものに出会うまでに3フェーズ分の儀式を読まされる——そして「必要に応じてスキーマを更新」は、最もユーザーの目が必要だった決定を隠している。

## 送信前の自己点検

- 最初のセクションは「フェーズ1：セットアップ」ではなく、ユーザーが最も変えそうな内容か？
- すべての決定が「Y ではなく X を選んだ、理由は Z」の形で、拒否できるように表現されているか？
- 機械的な作業は計画を膨らませず、末尾に圧縮されているか？
- 残存する未知を明示し、構築フェーズの実装ノートを準備したか？
- 計画を成果物として新セッションへ引き継ぐ提案をしたか？
