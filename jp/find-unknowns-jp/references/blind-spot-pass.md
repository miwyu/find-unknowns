# ブラインドスポットパス（未知の未知）

ユーザーのタスクが実際に触れる範囲をコードベースやウェブで調査し、「聞くべきだと知らなかったこと」を教える。アウトプットは報告書のための報告書ではない——ユーザーのプロンプトを書き換えるべき質問と制約のセットだ。

## 適用条件

- ユーザーが不慣れなドメイン、またはコードベースの不慣れな部分に入ろうとしている（「認証モジュールは触ったことがない」「カラーグレーディングが何か知らない」）。
- ユーザーが「ブラインドスポットパス」や「未知の未知」を名指しで求めた。
- まだ枠組みすら掴めていない事柄について、プロンプトの書き方を教えてほしいと言った。

ボトルネックが本当に「未知の未知」かを確かめること。ユーザーが自分で質問に答えられるならインタビューを、見れば分かるタイプならブレインストーム＆プロトタイプを使う。

## 手順

1. ユーザーの出発点を尋ねる（または推測する）：すでに知っていること、試したこと、このドメインに対する本人の立ち位置。すでに語られていればスキップ。
2. 実質的なことを言う前に現地を調査する。コードベースなら：タスクが触れるモジュール、その履歴、テスト、隣接機能を読む。ウェブなら：このドメインで「良い」とは何か、よくある失敗モード、専門家が使う語彙。
3. パスを4つの問いで構成する：ここにはどんな過去の作業があるか？ このドメインで「良い」とは何を指すか？ よくある失敗モードや落とし穴は？ 専門家なら聞くのにユーザーがまだ聞いていない質問は？
4. 見つけたものを順位づけする。未知はたいてい5個以上見つかるが、順位づけこそがあなたの付加価値だ。ユーザーにはまだ、荷重のかかる論点と些事の区別がつかない。
5. 上位3〜5個を「決定」として届け、残りは明示的に保留し、書き直したプロンプトを提案する（出力契約を参照）。

## 出力契約

返答には次を、この順で含める：

1. パターンの名乗り1行（「X についてブラインドスポットパスを実行しました——現地はこう言っています」）。
2. 短いレクチャー：未知を理解するのに必要な最小限のドメイン文脈——百科事典の項目ではなく直観を。
3. **影響の大きい未知を3〜5個。それぞれを「ユーザーがこれから下すべき決定」として表現する**——観察でも質問の羅列でもなく。「webhook のバーストをテナントのレート制限に含めるかどうかを決める必要があります」は「webhook があります」に勝る。
4. 残りの明示的な保留：「細かいものもいくつかあります——見ますか？」（保留項目の名前を挙げるだけなら3〜5個の上限に数えない。詳細まで並べたら数える。）
5. 発見を織り込んで元プロンプトを書き直す提案——すでに求められていれば書き直したプロンプトそのもの。

求められていない限り、穴埋めテンプレートや網羅的な一覧を添付しないこと。

## 良い例／悪い例

**良い例**（ユーザー：「レート制限を足したいけどこのミドルウェアは触ったことがない」）：

> レート制限まわりの現地にブラインドスポットパスをかけました——聞くべきだと知らなかったことが3つあります：
>
> 1. **エンタープライズ契約の下限。** `auth.js` にエンタープライズ顧客へ「1000 req/min 未満のスロットリング禁止」を約束するコメントがあります。決めること：制限はプラン対応の下限を持つテナント単位か、グローバルか？
> 2. **認証なしの webhook ルート。** `/webhooks/github` は認証を通らないため、ユーザーIDでキーイングすると静かに対象外になります。決めること：専用バケツを持たせるか？
> 3. **Redis のオフラインキューが無効。** Redis が瞬断すると呼び出しはキューに入らず例外を投げます。決めること：フェイルオープンかフェイルクローズドか？
>
> 細かいものもいくつかあります（テストの glob が壊れている、参照されている statsd が存在しない）——それも見ますか？ よければ、この3つの決定を織り込んだ形にプロンプトを書き直します。

**悪い例**（同じ依頼）：

> レート制限は大きなトピックです！ 考慮事項が14個あります：アルゴリズム（トークンバケット、スライディングウィンドウ、固定ウィンドウ…）、ストレージの選択肢、分散協調、HTTP 429 のセマンティクス、Retry-After ヘッダー、…… 先に進むため、この要件テンプレートを埋めてください：[20行の表]。

悪い例は3重に失敗している：*この*コードベースを読む代わりに一般論のドメイン講義をし、順位づけのない一覧を投げ、宿題を手渡している。ユーザーは依然として、どの決定に荷重がかかっているのか分からないままだ。

## 送信前の自己点検

- 現地（コードベース／ウェブ）を実際に調査したか？ 一般的なドメイン知識を暗唱していないか？
- 提示した項目はすべて、調査で見つけた事実に根ざした**ユーザーが下すべき決定**として表現されているか？
- 提示項目は5個以下で、残りは明示的に保留・提案されているか？
- 書き直したプロンプトを提案した（求められていれば届けた）か？
- 誰も頼んでいない穴埋めテンプレートや網羅チェックリストが返答に混ざっていないか？ あれば削る。
