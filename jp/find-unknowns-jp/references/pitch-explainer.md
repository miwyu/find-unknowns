# ピッチ／説明資料（実装後）

レビュアーは、ユーザーがかつて持っていたのと同じ未知からスタートする。良いピッチ資料はその道筋をなぞり直す：まずデモか成果を見せ、次に下した判断と、潰しておいた失敗ポイント——専門家のレビュアーが突いてくる箇所——を示す。目的は、賛同と承認を、より速く得ることだ。

## 適用条件

- 作業が完成し、他者の賛同が必要：PR の説明、Slack でのピッチ、設計レビュー資料。
- ユーザーが「レビュアー／ステークホルダー／承認者向けにまとめて」と言った。
- 以前のパターンの成果物（プロトタイプ、仕様、実装ノート）があり、共有可能なひとつの文書にする必要がある。

読み手が「マージ前に変更を理解する必要のある*ユーザー本人*」なら、代わりにクイズパターンを——このパターンは他者を納得させるためのものだ。

## 手順

1. 読み手が誰で、どこに投稿するのかを（自明でなければ、一度だけ短く）尋ねる——PM への Slack ピッチとスタッフエンジニア向けの PR 説明では突かれる場所が違う。
2. 成果を先頭に：デモ、GIF、スクリーンショット、前後の数字。レビュアーは散文ではなく証拠から信頼を広げる。
3. 未知をたどった道筋を圧縮して示す：難しかった決定は何で、何を選んだか——レビュアーが押してきそうな2〜4個。全部ではない。
4. 専門家の追及を先回りする：このドメインの経験者が聞いてくる失敗ポイント（競合、ロールバック、上限、マイグレーション安全性）に、それぞれ1行の答えを。実装ノートの Deviations はここの素材の宝庫だ——記録された逸脱は、まさにレビュアーが見つけたであろう類のものだから。
5. プロトタイプ・仕様・実装ノートをひとつの成果物にまとめる（またはそこからリンクする）。ユーザーが Slack や PR の説明にそのまま貼れる1文書に。

## 出力契約

自己完結した文書ひとつを、この順で：

1. **成果** — デモリンク／GIF／スクリーンショット／数字と、何が出荷されたかの一文。
2. **決定** — 荷重のかかった選択2〜4個。各項目：何を選んだか、何を却下したか、なぜか。
3. **何がまずくなり得て、どう対処したか** — 専門家の追及リストと1行の答え。
4. **リンク** — プロトタイプ、仕様、実装ノート、diff。

長さ：Slack 形式なら2分以内で読める分量。PR 説明ならもう少し長くてよい。そのまま貼れることが条件——ユーザーにしか録れないものを除き、「[ここにデモを挿入]」のようなプレースホルダーを残さない。

## 良い例／悪い例

**良い例**（Slack ピッチの冒頭）：

> **非同期リファンドが staging で動いています** — [30秒のデモGIF]。リファンドの決済が、チェックアウトを30秒ブロックする代わりに約2秒で完了するようになりました。
>
> 押されそうな決定2つ：
> - **失敗したリファンドはデッドレターに、ただし大声で** — ページャーアラート＋管理キュー。無限サイレントリトライ（実質、失敗を失う旧挙動）ではなく。
> - **冪等性はクライアントキー必須** — サーバー側フォールバックなし。タイムスタンプのフォールバックはリトライを壊すため。
>
> 当然の追及への先回り：処理中の再起動 → ジョブ状態は Postgres にあり、きれいに再開。二重送信 → 冪等性キーが重複排除…

**悪い例**（同じ変更）：

> この PR はリファンドフローをリファクタリングします。変更ファイル：`refund.js`（処理をワーカーへ移動）、`queue.js`（新規）、`api.js`（エンドポイントが 202 を返すように）… [さらに12ファイルの説明] …processRefund 関数は3つのヘルパーに分割されました。質問があれば言ってください。

悪い例は diff のナレーションだ——レビュアーが信頼するのに必要なものではなく「何が変わったか」を記述している。冒頭に成果がなく、賛否を表明できる決定がなく、失敗モードを検討した証拠がない。「質問があれば言ってください」は、ピッチがやるはずだった仕事そのものを外注している。

## 送信前の自己点検

- 読み手が最初に目にするものは、動いている成果か——背景説明やファイル一覧ではなく？
- 決定は「Y ではなく X を選んだ」の形で、レビュアーがうなずく以外の関与をできるか？
- その部屋で一番懐疑的な専門家が聞く2〜4個の質問に答えたか？ Deviations ログの内容を含めたか？
- そのまま貼れる1つの成果物になっているか——チャット内の要約＋ユーザーが組み立てる散らばったリンク、になっていないか？
- 想定読者が実際に割く時間内に読み切れるか？
