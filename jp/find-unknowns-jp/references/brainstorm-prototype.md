# ブレインストーム＆プロトタイプ（未知の既知）

ユーザーが「反応することでしか自分の欲しいものを知れない」とき、反応する対象を生成する。目的は、本人が言語化できない好みと要件を——実装で高くつく前に、安く——表に出すことだ。実装の途中で発覚した「未知の既知」は手戻りを強いる。ここで発覚すれば、却下されたスケッチひとつ分のコストで済む。

## 適用条件

- ユーザーが何らかの形で「見れば分かる」と言っている：ビジュアルデザイン、UX、命名、トーン、API の使い心地。
- 却下した試作はあるが理由を説明できない（「自分で作った3バージョンとも嫌だった」）。
- 生煮えのアイデアがあり、コミットする前にスコープを探索したい。

リダイレクト：ユーザーが既存の実例を**名指しした**（「X みたいに」）→ リファレンス探し。欲しいものについて質問に答えるだけで済むなら → インタビュー。「好みを言語化できない」と言ったユーザーに、前提条件としてそれを説明させないこと——それこそ本人が「できない」と伝えてきた唯一のことだ。

## 入力

- ユーザーの依頼と、すでに報告された却下済みの試作や反応。
- 問題になっている好みの次元（レイアウト？ 密度？ トーン？ アプローチ？）——不明なら、それがこのパターンで許される唯一の質問。候補と並べて、同じターンで聞く。

## 手順

1. 候補が変化する次元を固定する。それ以外（内容、データ）は一定に保ち、反応が好みだけを切り出すようにする。
2. **本当に異なる方向性を3〜5個**作る——異なるレイアウト、メタファー、野心のレベルであって、ひとつのアイデアのバリエーションではない。バリエーションは、どうせ収束していた地点にユーザーの反応を浪費する。
3. すべての候補を構造的に安く保つ：ハードコードしたダミーデータ入りの自己完結した単一HTMLファイル、または1段落のスケッチ。バックエンドなし、ビルドステップなし、実インテグレーションなし——それが必要な候補は、作らずに説明で済ませる。
4. ユーザーに反応を求める：選ぶ、却下する、混ぜる——一文で十分。
5. 反応が返ったら、それを明示的な要件に翻訳し（「密度の高いレイアウトを全部却下しましたね。つまり情報密度は本物の制約です」）、確認してもらう。この翻訳こそが成果物で、モックは足場だ。

## 初回ターンの契約

1. パターンの名乗りと、候補が何の次元で異なるのかを1行で。
2. 候補3〜5個。それぞれに「何が違うのか」の1行説明——何のファイルも開かずに読める形で。
3. 締めの反応の問いかけひとつ：「どれが一番近いですか？ そしてそれの何が違いますか？」（任意で、添え物として：「気に入っている既存のページがあれば教えてください」。）
4. 抽象的な好みについての必須アンケートは無し。微調整用に提示される単一の「完成」ビルドも無し。

## 成果物

初回ターン：候補セット。反応後：明らかになった要件の確認可能なリスト。次のパターン（通常は実装計画）へ持ち込む。

## 停止条件

- 候補は5個で生成をやめる。それ以上は反応を薄める。
- ユーザーの反応を要件として復唱し、確認できたらパターンを終える——そのうえで計画または実装へ引き継ぐ。パターンの途中でユーザーが既存の実例を名指ししたら、リファレンス探しへ切り替える。

## 良い例／悪い例

**良い例**（ユーザー：「このデータのダッシュボードが欲しいけど、視覚的センスが全然ない」）：

> ブレインストームの回です——密度と階層の異なる4方向、すべてダミーデータ入りの単一HTMLです：
>
> 1. **密なグリッド** — 全部見える、スプレッドシートの気配。
> 2. **一枚看板** — 数字ひとつ、他はワンクリック先。
> 3. **物語スクロール** — 読み順に並ぶチャートとキャプション。
> 4. **ターミナル** — 等幅、キーボード主体、装飾なし。
>
> `mockups.html` を開いて、どれが一番近いか・それの何が違うかを教えてください——却下も選択と同じくらい情報になります。

**悪い例**（同じ依頼）：

> サイドバー、チャートパネル4枚、設定ページ付きのダッシュボードを作って、あなたの API に配線しました。微調整があれば言ってください！

悪い例は、一般的ベストプラクティスで選んだひとつの方向にコミットし、形がユーザーの目に触れる前に実インフラを配線し、本当の未決事項が全体の形なのに細部への反応を招いている。

## 送信前の自己点検

- 候補は3〜5個で、それぞれバリエーションではなく本当に異なる方向か？
- 変化しない内容は候補間で同一（またはほぼ同一）に保たれているか？
- すべての候補はダミーデータで、実配線なし、ビルドステップなしか？
- ユーザーは一文で反応できるか？
- 抽象的な好みの質問を必須ステップにしていないか？
- 反応後：それを明示的で確認可能な要件として復唱したか？
