# ブレインストーム＆プロトタイプ（未知の既知）

ユーザーが「反応することでしか自分の欲しいものを知れない」とき、反応する対象を生成する。目的は、本人が言語化できない好みと要件を——実装で高くつく前に、安く——表に出すことだ。

## 適用条件

- ユーザーが何らかの形で「見れば分かる」と言っている：ビジュアルデザイン、UX、命名、トーン、API の使い心地。
- 生煮えのアイデアがあり、コミットする前にスコープを探索したい（「オンボーディング後に離脱される——そもそもどこに介入できる？」）。
- 実システムを配線せずに、何かの見た目や感触を確かめたい。

欲しいものの実例がどこかに既に存在するなら、リファレンス探しを優先する——実例をひとつ読むほうが候補を多数生成するより安い。ユーザーが質問に答えるだけで済むならインタビューを。

## 手順

1. ユーザーが反応すべき次元（レイアウト？ 密度？ トーン？ アプローチ？）を確定する——自明でなければ短い質問ひとつで。
2. **方向性が本当に異なる案**を複数作る——ひとつのアイデアのバリエーションではなく。異なるレイアウト、異なるメタファー、異なる野心のレベル。単一テーマのバリエーションは、どうせ収束していた地点にユーザーの反応を浪費する。
3. 各候補は可能な限り安く：ダミーデータ入りの単一HTMLモック、安い順に並べた10案リスト、実配線前のスケッチ。モックのためにバックエンドの配管を作らないこと。
4. ユーザーに反応してもらう——選ぶ、却下する、混ぜる。
5. 反応が**明らかにしたこと**を明示的な要件として記録する：「密度の高いレイアウトを全部却下しましたね。つまり情報密度は本物の制約です」。この翻訳ステップこそが納品物であり、モックは足場にすぎない。

早い段階でやる理由：実装の途中で発覚した「未知の既知」は高くつく。仕様の小さな変更が実装の大幅な違いになり得るし、作りかけの巻き戻しは、別のスケッチを選び直すより難しい。

## 出力契約

1. パターンを名乗り、候補が何の次元で異なるのかを言う。
2. 候補を3〜5個届ける（モック、スケッチ、または順序付きアプローチリスト）。各候補に「何が違うのか」の1行説明を付ける——何も開かずに反応できる程度に。
3. 反応を求めるひとことで締める：「どれが一番近いですか？ そしてそれの何が違いますか？」
4. ユーザーの反応後：反応が明らかにした要件を、確認できる明示的な文として復唱し、次のパターン（通常は実装計画）へ持ち込む。

データはすべてダミー。実インテグレーションは無し。数分で作れない候補はこの段階には高すぎる——代わりに説明で済ませる。

## 良い例／悪い例

**良い例**（ユーザー：「このデータのダッシュボードが欲しいけど、視覚的センスが全然ない」）：

> ブレインストームの回です——密度と階層の異なる4方向、すべてダミーデータ入りの単一HTMLです：
>
> 1. **密なグリッド** — 全部見える、スプレッドシートの気配。
> 2. **一枚看板** — 数字ひとつ、他はワンクリック先。
> 3. **物語スクロール** — 読み順に並ぶチャートとキャプション。
> 4. **ターミナル** — 等幅、キーボード主体、装飾なし。
>
> `mockups.html` を開いて、どれが一番近いか・それの何が違うかを教えてください——却下も選択と同じくらい情報になります。

**悪い例**（同じ依頼）：

> サイドバー、チャートパネル4枚、設定ページ付きのダッシュボードを作って、あなたの API に配線しました。微調整があれば言ってください！

悪い例はひとつの方向（ユーザーの好みではなく一般的ベストプラクティスで選んだ）にコミットし、レイアウトがユーザーの目に触れる前に実インフラを配線し、「微調整」を求めている——本当の未決事項が全体の形なのに、細部への反応を招いている。

## 送信前の自己点検

- 候補は本当に異なる方向か？ ひとつのアイデアのバリエーションになっていないか？
- 各候補は可能な限り安いか——ダミーデータで、実配線なしか？
- ユーザーは一文で反応できるか？ 宿題を手渡していないか？
- 反応後：フィードバックを黙って反映するのではなく、確認可能な明示的要件に翻訳したか？
