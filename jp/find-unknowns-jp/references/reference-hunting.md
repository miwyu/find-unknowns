# リファレンス探し

ユーザーが欲しいものをうまく説明できないとき、既存の実例——正しくやっているライブラリ、好きなデザイン、リポジトリ内の似た機能——は本人より雄弁だ。リファレンスを見つけ、移植可能な本質を抽出し、どの性質が実際に重要かを確認する。

## 適用条件

- ユーザーが実例を指した：「Stripe のエラーみたいに」「この crate みたいに」「うちにすでにある検索機能みたいに」。
- ユーザーが欲しいものを詳細に言語化できず、本人が思いついていない具体的な実例が存在すると疑われる。

リダイレクト：実例がどこにも存在しない、または欠けているのが名指しできる手本のない好みなら → ブレインストーム＆プロトタイプ。空白がユーザーが単に答えられる類のものなら → インタビュー。

## 入力

- 名指しされた（または疑われる）リファレンス：ソースコード、ドキュメント、プロダクト、このリポジトリ内の機能。形式としては**ソースコード**を最優先する——言語が違っても、コードはスクリーンショットや散文には載らないエッジケースの扱い・状態の形・順序保証を運ぶ。
- ユーザーの文脈（スタック、その挙動が置かれる場所）——移植可能なものと付随物を分離するために。

## 手順

1. まだリファレンスが名指しされていなければ：**質問ひとつ**——実例はあるか？——を、ありそうな具体的な場所2〜3個（ライブラリ、敬愛するプロダクト、このリポジトリ内の似た機能）とともに聞く。そこで止める。それがターンの全部だ。
2. リファレンスを得たら読む——届く限り、評判の記憶ではなく実際のソースやドキュメントを。
3. **移植可能な本質**を抽出する：再実装する価値のある挙動・不変条件・構造。付随物は脇に置く：言語のイディオム、命名規約、リファレンス自身の技術スタックの制約。
4. 抽出結果を**3〜7個の性質、それぞれ挙動として表現**して復唱する（「リトライはフルジッター、上限30秒」）——コードツアーではなく。
5. どの性質が本質でどれが付随物かをユーザーに尋ねる——リファレンスは*ユーザーの*代理仕様なのだから、裁定者はユーザーだ。確認済みリストを仕様として持ち込む。

## 初回ターンの契約

- **リファレンス未取得：** パターンの名乗り1行＋質問ひとつ＋候補の場所2〜3個。それ以外は何もなし——ゼロから生成した候補もなし、実装もなし。
- **リファレンス取得済み：** パターンの名乗り1行。挙動レベルの性質3〜7個。確認の問いかけひとつ（「このうちどれが必須ですか？ あなたが実際に気に入っていた点を見落としていませんか？」）。確認済みリストを計画または実装へ持ち込む申し出。目標の形を示す短い例示は許される。ユーザーのシステムの書き換えは許されない。

## 成果物

確認済みの性質リスト——ユーザーの代理仕様を明示化したもの。実装計画または構築に直接つながる。

## 停止条件

- 性質は7個で抽出をやめる。それ以上が本質に見えるなら、超過分は1行の保留に入れる。
- 確認の問いかけでターンを止める——未確認の性質に対して実装しない。
- ユーザーが「実例はない」と言ったら、食い下がらずにブレインストーム＆プロトタイプへ切り替える。

## 良い例／悪い例

**良い例**（ユーザー：「vendor にある Rust crate みたいなバックオフを、うちの TS クライアントに」）：

> `vendor/rate-limiter` でリファレンス探しをしました。Rust 特有の部分を剥がした移植可能な本質はこれです：
>
> 1. **フルジッター**付き指数バックオフ（0から指数上限までの乱数）。イコールジッターではない。
> 2. リトライ予算は**エンドポイント単位**、グローバルではない——ホットなエンドポイントひとつが他を飢えさせない。
> 3. `Retry-After` ヘッダーがあれば計算した遅延を上書きする。
> 4. 4xx ではリトライ停止。ただし 429 は除く。
>
> 4つとも必須ですか？ 特に #2 はクライアントの構造を変えます——不要なら、ずっと単純になります。

**悪い例**（同じ依頼）：

> crate を1行ずつ解説します：`lib.rs` は `base`、`cap`、`rng` フィールドを持つ `Backoff` 構造体を定義していて… [200行] …また、Rust のトレイトを同じモジュール構成のまま TypeScript のインターフェースに翻訳しておきました。

悪い例は抽出ではなく転写だ——本質と一緒に付随物（モジュール構成、構造体の形）まで保存し、ユーザーが実際に欲しかった性質はどれかを一度も聞かず、肝心の4つの挙動を埋もれさせている。

## 送信前の自己点検

- リファレンスがなかった場合：返信は質問ひとつ＋候補の場所2〜3個だけになっているか？
- リファレンスを読んだ場合：性質は3〜7個で、それぞれ挙動として表現され、付随物は剥がされているか？
- 全性質を必須と決めつけず、どれが必須かをユーザーに確認したか？
- 未確認の性質に対する実装を思いとどまったか？
- 確認済みリストを入力として、次のステップ（計画または実装）を申し出たか？
