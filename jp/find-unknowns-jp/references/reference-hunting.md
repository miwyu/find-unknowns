# リファレンス探し

ユーザーが欲しいものをうまく説明できないとき、既存の実例——正しくやっているライブラリ、好きなデザイン、リポジトリ内の似た機能——は本人より雄弁だ。あなたの仕事は、リファレンスを見つけ、移植可能な本質を抽出し、どの性質が実際に重要かを確認することだ。

## 適用条件

- ユーザーが欲しいものを詳細に言語化できない——語彙がない、または説明に時間がかかりすぎる。
- ユーザーが実例を指した：「あの crate みたいに」「Stripe のドキュメントみたいに」「うちの検索機能みたいに」。
- 実例がありそうなのにユーザーが思いついていない——ブレインストームの前に尋ねること。実例をひとつ読むほうが候補を多数生成するより安い。

実例がどこにも存在しないときだけ、ブレインストーム＆プロトタイプに戻る。

## 手順

1. 実例の有無を尋ねる。ありそうな場所を添えて：その挙動を実装しているライブラリ、デザインが好きなプロダクト、このリポジトリ内の似た機能。質問はひとつ、具体的な候補源とともに。
2. リファレンスの形式としては**ソースコード**を最優先する——言語が違っても。コードはスクリーンショットや説明文には載らない構造と意味を運ぶ：エッジケースの正確な扱い、状態の形、順序保証。
3. リファレンスを読む。**移植可能な本質**（再実装する価値のある挙動・不変条件・構造）と、付随物（言語のイディオム、命名規約、そのプロジェクト固有の技術的制約）を分離する。
4. 抽出結果を短い性質リストとしてユーザーに復唱し、どの性質が重要かを確認する——リファレンスは*ユーザーの*代理仕様なのだから、何が本質で何が偶然かの裁定者はユーザーだ。
5. 確認済みの性質リストを、実装または計画の仕様として持ち込む。

## 出力契約

1. パターンを名乗る。まだリファレンスがなければ、返答は質問ひとつ（「実例はありますか？」）＋ありそうな場所2〜3個——それだけ。
2. リファレンスを読んだら：抽出した移植可能な性質の短いリスト（3〜7項目）。それぞれ挙動として表現する（「リトライはフルジッター、上限30秒」）——コードツアーではなく。
3. 確認の問いかけ：「このうちどれが必須ですか？ あなたが気に入っていた点を見落としていませんか？」
4. 確認済みリストが仕様という成果物になる——それを持って計画または実装へ進むことを提案する。

## 良い例／悪い例

**良い例**（ユーザー：「vendor にある Rust crate みたいなバックオフを、うちの TS クライアントに」）：

> `vendor/rate-limiter` でリファレンス探しをしました。Rust 特有の部分を剥がした移植可能な本質はこれです：
>
> 1. **フルジッター**付き指数バックオフ（0から指数上限までの乱数）。イコールジッターではない。
> 2. リトライ予算は**エンドポイント単位**、グローバルではない——ホットなエンドポイントひとつが他を飢えさせない。
> 3. `Retry-After` ヘッダーがあれば計算した遅延を上書きする。
> 4. 4xx ではリトライ停止。ただし 429 は除く。
>
> 4つとも必須ですか？ 特に #2 はクライアントの構造を変えます——不要なら、ずっと単純になります。

**悪い例**（同じ依頼）：

> crate を1行ずつ解説します：`lib.rs` は `base`、`cap`、`rng` フィールドを持つ `Backoff` 構造体を定義していて… [200行] …また、Rust のトレイトを同じモジュール構成のまま TypeScript のインターフェースに翻訳しておきました。

悪い例は抽出ではなく転写だ——本質と一緒に付随物（モジュール構成、構造体の形）まで保存し、ユーザーが実際に欲しかった性質はどれかを一度も聞かず、肝心の4つの挙動を埋もれさせている。

## 送信前の自己点検

- ゼロから候補を生成する前に、実例の有無を尋ねたか？
- リファレンスを読んだ場合：出力は**挙動レベルの性質リスト**か？ コードツアーや機械的翻訳になっていないか？
- 移植可能な本質と、リファレンス固有の偶然の選択を分離したか？
- 全性質を必須と決めつけず、どれが必須かをユーザーに確認したか？
