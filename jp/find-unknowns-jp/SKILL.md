# Find Unknowns（未知の発見）

エージェンティックな作業の品質を決めるボトルネックは「未知」である。ユーザーが依頼した内容と、作業が実際に要求するものとのギャップだ。いま質問ひとつ・プロトタイプひとつ・短いレクチャーひとつで安く解消できる未知は、後で高くつく巻き戻しをひとつ減らす。あなたの役割はファシリテーションだ。以下の6ステップを順に実行し、パターンをちょうど1つ（多くても2つ）選び、それを自ら実行すること。フレームワークの解説や選択肢の列挙で終わらせてはいけない。

## ステップ0 — 非適用チェック

作業が定型なら、パターンも追加のプロセスも使わず、ユーザーに直接答える：原因の明確なエラーのデバッグ、小さく範囲の明確な修正、事実確認の質問。そして、ユーザーが閉じた決定を決して蒸し返さないこと：合意済みの仕様は後段パターンへの確定済み入力であり、インタビューし直す対象ではない。（計画からの構築にも、完成した作業のレビューにもパターンはある——表を参照——つまり閉じた決定はライフサイクルを前へ進める経路であって、後戻りさせる経路ではない。）

## ステップ1 — ステージ確認

作業がライフサイクルのどこにいるかを分類する。これが最初のルーティング判断であり、決定的だ：

- **作業が完成している**（マージ済み、ビルド済み、完了）→ 実装後のパターンのみ。読み手が「納得させるべき他者」→ **ピッチ／説明資料**。読み手が「理解する必要のあるユーザー本人」→ **クイズ**。完成した作業を発見フェーズに引き戻してはならない。
- **実装の最中**、または既存の計画／仕様の実装を頼まれた → **実装ノート**（構築し、逸脱を保守的に記録する）。
- **実装前**（何を作るかを決めている段階）→ ステップ2へ。

## ステップ2 — パターン選択（実装前のみ）

以下の規則を**順に適用する。最初に一致したものが勝つ**：

1. **明示的な依頼が最優先。** ユーザーがパターンまたはその成果物を名指しした——「インタビューして」「ブラインドスポットパス」「計画を書いて」「クイズを出して」「これをピッチして」→ そのパターン。
2. **名指しされた実例** — ユーザーがすでに存在するものを指した（「Stripe のエラーみたいに」「あの crate みたいに」「うちの検索機能みたいに」）→ **リファレンス探し**。実例をひとつ読むほうが多数生成するより優れている。
3. **言語化できない好み** — ユーザーが何らかの形で「見れば分かる」と言っている、または却下した試作はあるのに理由を説明できない（ビジュアルデザイン、UX、命名、トーン）→ **ブレインストーム＆プロトタイプ**。「説明できない」と本人がすでに伝えているのだから、説明させないこと。反応できる方向性を生成する。（*気に入っている*実例の有無を尋ねるのは、同じ返信内の任意の添え物としてのみ許される。）
4. **不慣れな領域** — ユーザーがそのドメイン、ライブラリ、コードベースのその部分に不慣れ → **ブラインドスポットパス**。聞く前に調べる：現地は、ユーザーが答えなくていい質問に答えてくれる。
5. **答えられる空白のある仕様** — 固い意図はあるが、聞けばユーザーが決められる未決事項がある → **インタビュー**。
6. **要件は確定、コードの前に決定のレビューが必要** → **実装計画**。計画は発見の出口だ：残った曖昧さがアーキテクチャを変えるなら、それは規則5であってこれではない。

ユーザーの出発点（ライフサイクルの段階、慣れ、意図の固さ）が不明なら、1通の短いメッセージで尋ねる——アンケート形式にしない。コードベースが手元にあるなら、診断の間に中を見る。見つけたものは推測に優先する。

実行するパターンは**1つ**。2つ目を足すのは、選んだ参照ファイル自体があなたをリダイレクトするときだけ（その「適用条件」セクションにハンドオフ先が書かれている）。実行するパターンの名前を1行で伝えること。ユーザーが語彙を学べる。

## ステップ3 — 参照ファイルを読む

選んだパターンの `references/<pattern>.md` だけを読む——8つ全部は決して読まない：

| パターン | ファイル |
|---|---|
| ブラインドスポットパス | `references/blind-spot-pass.md` |
| ブレインストーム＆プロトタイプ | `references/brainstorm-prototype.md` |
| インタビュー | `references/interview.md` |
| リファレンス探し | `references/reference-hunting.md` |
| 実装計画 | `references/implementation-plan.md` |
| 実装ノート | `references/implementation-notes.md` |
| ピッチ／説明資料 | `references/pitch-explainer.md` |
| クイズ | `references/quiz.md` |

すべてのファイルは同じセクション構成を持つ：適用条件／入力／手順／初回ターンの契約／成果物／停止条件／良い例・悪い例／送信前の自己点検。チャット返答の骨格はこれらのファイルの中にある。ユーザーのリポジトリへコピーする唯一のファイルは `assets/implementation-notes-template.md`（実装ノートパターン）だ。

## ステップ4 — 実行

参照ファイルの「手順」と「初回ターンの契約」に従う。以下のガードレールはすべてのパターンを拘束し、そして数えられる：

- **必須の質問は1ターンにつき最大1つ。** 任意の文脈提供の申し出（「リポジトリを共有してもらえれば自分で読み取ります」）は質問に数えない。2つ目の必須質問は数える。
- **提示する決定／項目は1ターンにつき最大5個。** 5を超える分はすべて1行の申し出で保留する（「細かいものもあります——見ますか？」）。保留トピックの名前を挙げるだけなら5個に数えない。説明したら数える。
- **求められていない限り、穴埋めテンプレートや網羅チェックリストは出さない。** 後で出すと申し出るのは良い。添付するのはだめだ。
- **毎ターン、ユーザーがいますぐ行動できるもので終える**：決定リスト、質問、モック、計画、書き直したプロンプト——次の一手のない「あなたの未知はこれです」ではなく。
- **構築中に現実が計画と矛盾したら、最も安く巻き戻せる選択肢を取り、記録して、進み続ける。**
- **儀式の規模は賭け金に合わせる。** 小さなタスクなら、明確化の質問ひとつがパターンの全部でよいこともある。

これらが存在するのは、パターンが宿題のように届いた瞬間に失敗するからだ。ユーザーは「何を聞けばいいか分からない」状態で来ているのに、質問の形をした16項目を渡されても、どこから手をつければいいか分からないまま、読む量だけが増える。回答が返るたびに次に聞く価値のあることが変わるので、目録を前倒しで並べても得るものはない。

## ステップ5 — 送信前の自己チェック

選んだ参照ファイルの「送信前の自己点検」を、返信の下書きに対して実行する。各項目は yes/no で答えられる。送信前にすべての「no」を直すこと——「no」があると知りながら送信してはならない。

## 背景：4つの象限

表の背後にある語彙。診断を声に出すときに有用：

- **既知の既知（Known knowns）** — ユーザーが伝えてくれたこと：プロンプトそのもの。
- **既知の未知（Known unknowns）** — 聞けばユーザーが答えられる空白 → インタビュー。
- **未知の既知（Unknown knowns）** — 見れば分かるが言語化できない好み → 選択肢を見せる（ブレインストーム／プロトタイプ）か、既存の実例を見つける（リファレンス探し）。
- **未知の未知（Unknown unknowns）** — 聞くべきだと知らない質問 → ブラインドスポットパス：調査し、それから教える。

同じタスクにはたいてい4つすべてが含まれる。いまのボトルネックがパターンを決める。
