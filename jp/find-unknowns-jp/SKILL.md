# Find Unknowns（未知の発見）

エージェンティックな作業の品質を決めるボトルネックは「未知」である。ユーザーが依頼した内容（地図）と、作業が実際に要求するもの（現地）とのギャップだ。いま質問ひとつ・プロトタイプひとつ・短いレクチャーひとつで安く解消できる未知は、後で高くつく巻き戻しをひとつ減らす。このスキルでのあなたの役割はファシリテーターだ。どの未知が支配的かを診断し、適切なパターンを選び、それを自ら実行すること。フレームワークの解説や選択肢の列挙だけで終わらせてはいけない。

## このスキルを使うとき

- ユーザーが名指しで求めたとき：「ブラインドスポットパス」「未知の未知」「unknown unknowns」「インタビューして」「もっと良いプロンプトの書き方を教えて」。
- ドメイン・ライブラリ・コードベースの一部に不慣れだと言ったとき。
- タスクが大きく・曖昧で・仕様が固まっておらず、そのまま実装に入れば要件を推測で埋めることになるとき——本人がこのプロセスを名指ししなくても。

## このスキルを使わないとき

- タスクがすでに完全に仕様化されている。
- 合意済みの仕様を、決定を蒸し返さずに実装してほしいと頼まれた。
- 定型作業である：原因の明確なエラーのデバッグ、小さく範囲の明確な修正。実装する準備ができているユーザーを発見フェーズに引き戻してはならない。

## 4つの象限

道具を選ぶ前に、状況を分類する：

- **既知の既知（Known knowns）** — ユーザーが伝えてくれたこと。プロンプトそのもの。
- **既知の未知（Known unknowns）** — まだ決めていないと本人が自覚していること。聞けば答えられる。→ *インタビューする。*
- **未知の既知（Unknown knowns）** — 言語化はできないが、見れば分かる好みや要件（「見れば分かる」）。→ *選択肢を見せる：ブレインストーム、プロトタイプ、バリエーション。*
- **未知の未知（Unknown unknowns）** — 聞くべきだと知らない質問。持っていないドメイン知識。結果がどこまで良くなり得るかの相場観。→ *ブラインドスポットパス：先に調査し、それから教える。*

同じタスクにはたいてい4つすべてが含まれる。重要なのは、いまどれがボトルネックかだ。

## パターンの選択

まずユーザーの出発点を把握する。伝えられていなければ、短く尋ねる（1通の短いメッセージで。アンケート形式にしない）：ライフサイクルのどこにいるか（これから始める／構築中／完成済み）、このドメインとコードベースのこの部分への経験、思考プロセスのどの段階か（生煮えのアイデアか、空白のある固い仕様か）。コードベースが手元にあるなら、診断の間に少し中を見ておくこと。現地は、ユーザーの前提のどれがすでに間違っているかを教えてくれる。それはどんな質問より価値がある。

そのうえで表からパターンを選び、そのパターンの参照ファイルを読む：

| 状況 | パターン | 読むファイル |
|---|---|---|
| 不慣れなドメイン、またはコードベースの不慣れな部分 | ブラインドスポットパス | `references/blind-spot-pass.md` |
| 「見れば分かる」——ビジュアルデザイン、UX、命名、トーン | ブレインストーム＆プロトタイプ | `references/brainstorm-prototype.md` |
| 仕様はあるが、聞けば埋まる空白がある | インタビュー | `references/interview.md` |
| 言葉にできないが、実例が存在する | リファレンス探し | `references/reference-hunting.md` |
| 実装準備完了。コードを書く前に論点を洗い出したい | 実装計画 | `references/implementation-plan.md` |
| 実装中。計画が現実とぶつかっている | 実装ノート | `references/implementation-notes.md` |
| 完成。他者の承認・賛同が必要 | ピッチ／説明資料 | `references/pitch-explainer.md` |
| 完成。マージ前にユーザー自身が理解する必要がある | クイズ | `references/quiz.md` |

## 複数のパターンが当てはまるとき

1. **ライフサイクルが最優先。** 作業が完成しているなら実装後のパターン（ピッチかクイズ）を選ぶ——完成したタスクを発見フェーズに引き戻してはならない。構築中なら実装ノート。
2. **質問より先に現地。** ブラインドスポットパスとインタビューの両方が当てはまるとき（不慣れなドメイン*かつ*仕様の空白）は、ブラインドスポットパスを先に。調査はユーザーが答えなくていい質問に答えてくれるし、見つかったものが「聞く価値のある質問」を組み替える。
3. **生成した選択肢より既存の実例。** ユーザーが欲しいものを言語化できないときは、ブレインストームの前に実例の有無を尋ねる——ひとつ読むほうが多数生成するより安い。実例がどこにもないときだけブレインストーム＆プロトタイプに戻る。
4. **計画は出口であって入口ではない。** 実装計画に手を伸ばすのは、残った曖昧さがアーキテクチャを変えなくなったときだけ。変えるなら、先にインタビュー。
5. **実行するのは1つか2つのパターン。8つ全部ではない。** このフレームワークは診断ツールであって、チェックリストではない。パターンを完遂して成果物を渡し、次に何をやるかはユーザーの反応に決めさせる。

どのパターンをなぜ実行するのか名前を挙げて伝えること。ユーザーが次回から語彙として使えるようになる。

## ガードレール（全パターン共通）

- **最初のターンは軽く。** これらのパターンは、宿題のように届いた瞬間に失敗する。ユーザーは「何を聞けばいいか分からない」状態で来ているのに、返答が質問＋チェックリスト＋穴埋めテンプレートの16項目だったら、読む量が増えただけで、依然としてどこから手をつければいいか分からない。守るべき規律は「順位づけ・上限・保留（rank, cap, and defer）」だ。必須の質問は**ひとつ**だけ。提示する論点は影響の大きい**ほんの一握り（3〜5個）**まで。それ以外はすべて手元に留める。深掘りは差し出すのではなく提案する（「論点の全リストや記入式の仕様書、要りますか？」）——テンプレートや網羅的な一覧は、最初の回答の後か、求められたときに出す。これが機能するのは、プロセスがそもそも反復的だからだ。回答が返るたびに次に聞くべきことが変わるので、最初に全部並べても得るものはない。
- **儀式の規模は賭け金に合わせる。** 1ファイルのバグ修正にインタビューは要らない。フルコースは、大きい・曖昧・不慣れな領域の作業のために取っておく。それ以外では、明確化の質問ひとつがパターンの全部でよいこともある。
- **必ず、ユーザーがすぐ行動できる成果物で終える**：書き直したプロンプト、確認済みの仕様、計画、少数の決定事項。「あなたの未知はこれです」だけで「で、どうするか」がなければ、ユーザーは出発点に立ち尽くしたままだ。ただし成果物とは*いま*行動できるもののこと——何かが起きる前にユーザーが埋めねばならない空白のテンプレートは、成果物ではなく追加の宿題だ。テンプレートは、求められたときかインタビューが終わったときのために取っておく。
- **具体性のバランスを取る。** 失敗モードは対称的だ。指示が具体的すぎれば、Claude は悪い計画のまま崖から落ちるまで従う。曖昧すぎれば、ユーザーの実際の意図の代わりに一般的なベストプラクティスで埋める。ここにあるすべてのパターンの目的は、ユーザーの次のプロンプトをその両極の間に着地させることだ。

## 参照ファイルの読み方

選んだパターンのファイル**だけ**を読む（優先規則に従い最大2ファイル）——8つ全部は読まない。すべての参照ファイルは同じ5セクションで構成されている：

1. **適用条件** — 実行に入る前に診断を確かめる。
2. **手順** — 実行するステップ。
3. **出力契約** — 返答が取るべき形。
4. **良い例／悪い例** — 違いを示す対照1組。
5. **送信前の自己点検** — 返答の下書きに対して送信前に実行する。

チャット返答の骨格や完成形のアウトラインは参照ファイルの中にある。ユーザーのリポジトリへコピーする唯一のファイルは `assets/implementation-notes-template.md`（実装ノートパターンで使用）だ。
