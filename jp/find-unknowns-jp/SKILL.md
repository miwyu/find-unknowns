# Find Unknowns（未知の発見）

エージェンティックな作業の品質を決めるボトルネックは「未知」である。ユーザーが依頼した内容（地図）と、作業が実際に要求するもの（現地）とのギャップだ。いま質問ひとつ・プロトタイプひとつ・短いレクチャーひとつで安く解消できる未知は、後で高くつく巻き戻しをひとつ減らす。このスキルでのあなたの役割はファシリテーターだ。どの未知が支配的かを診断し、適切なパターンを選び、それを自ら実行すること。フレームワークの解説や選択肢の列挙だけで終わらせてはいけない。

## 4つの象限

道具を選ぶ前に、状況を分類する：

- **既知の既知（Known knowns）** — ユーザーが伝えてくれたこと。プロンプトそのもの。
- **既知の未知（Known unknowns）** — まだ決めていないと本人が自覚していること。聞けば答えられる。→ *インタビューする。*
- **未知の既知（Unknown knowns）** — 言語化はできないが、見れば分かる好みや要件（「見れば分かる」）。→ *選択肢を見せる：ブレインストーム、プロトタイプ、バリエーション。*
- **未知の未知（Unknown unknowns）** — 聞くべきだと知らない質問。持っていないドメイン知識。結果がどこまで良くなり得るかの相場観。→ *ブラインドスポットパス：先に調査し、それから教える。*

同じタスクにはたいてい4つすべてが含まれる。重要なのは、いまどれがボトルネックかだ。

## ステップ1：診断

パターンを実行する前に、ユーザーの出発点を把握する。伝えられていなければ、短く尋ねる（1通の短いメッセージで。アンケート形式にしない）：

- **ライフサイクルのどこにいるか？** これから始める（実装前）、構築中（実装中）、完成していて理解・出荷が必要（実装後）？
- **このドメインとコードベースのこの部分への経験は？** 不慣れなコードにいる熟練者と、慣れたリポジトリにいる初心者では、必要なパスが違う。
- **思考プロセスのどの段階か？** 生煮えのアイデアにはブレインストームを、空白のある固い仕様にはインタビューを。

コードベースが手元にあるなら、診断の間に少し中を見ておくこと。現地は、ユーザーの前提のどれがすでに間違っているかを教えてくれる。それはどんな質問より価値がある。

そのうえで、以下から**1つか2つ**のパターンを選んで実行する。どのパターンをなぜ実行するのか名前を挙げて伝えること。ユーザーが次回から語彙として使えるようになる。

## ステップ2：適切なパターンを実行する

**最初のターンは軽く。** これらのパターンは、宿題のように届いた瞬間に失敗する。ユーザーは「何を聞けばいいか分からない」状態で来ているのに、返答が質問＋チェックリスト＋穴埋めテンプレートの16項目だったら、読む量が増えただけで、依然としてどこから手をつければいいか分からない。守るべき規律は「順位づけ・上限・保留（rank, cap, and defer）」だ。必須の質問は**ひとつ**だけ。提示する論点は影響の大きい**ほんの一握り（3〜5個）**まで。それ以外はすべて手元に留める。深掘りは差し出すのではなく提案する（「論点の全リストや記入式の仕様書、要りますか？」）——テンプレートや網羅的な一覧は、最初の回答の後か、求められたときに出す。これが機能するのは、プロセスがそもそも反復的だからだ。回答が返るたびに次に聞くべきことが変わるので、最初に全部並べても得るものはない。

| 状況 | パターン |
|---|---|
| 不慣れなドメイン、またはコードベースの不慣れな部分 | ブラインドスポットパス |
| 「見れば分かる」——ビジュアルデザイン、UX、命名、トーン | ブレインストーム＆プロトタイプ |
| 仕様はあるが、聞けば埋まる空白がある | インタビュー |
| 言葉にできないが、実例が存在する | リファレンス |
| 実装準備完了。コードを書く前に論点を洗い出したい | 実装計画 |
| 実装中。計画が現実とぶつかっている | 実装ノート |
| 完成。他者の承認・賛同が必要 | ピッチ／説明資料 |
| 完成。マージ前にユーザー自身が理解する必要がある | クイズ |

### ブラインドスポットパス（未知の未知）

ユーザーのタスクが実際に触れる範囲をコードベースやウェブで調査し、「聞くべきだと知らなかったこと」を教える。アウトプットは報告書のための報告書ではない——ユーザーのプロンプトを書き換えるべき質問と制約のセットだ。

パスの構成軸：ここにはどんな過去の作業があるか？ このドメインで「良い」とは何を指すか？ よくある失敗モードや落とし穴は？ 専門家なら聞くのにユーザーがまだ聞いていない質問は？

締めくくりは、**影響の大きい未知を3〜5個**——それぞれを「ユーザーがこれから下すべき決定」として表現する——であり、網羅的な一覧ではない。たいてい5個以上見つかるはずだが、順位づけこそがあなたの付加価値だ。ユーザーにはまだ、荷重のかかる論点と些事の区別がつかないのだから。残りは提案に留め（「細かいものもいくつかあります——見ますか？」）、発見を織り込んで書き直した元プロンプトも提案する。

### ブレインストーム＆プロトタイプ（未知の既知）

ユーザーが「反応することでしか自分の欲しいものを知れない」とき、反応する対象を生成する。方向性が本当に異なる案を複数作ること——ひとつのアイデアのバリエーションではなく。そして各案は可能な限り安く：ダミーデータ入りの単一HTMLモック、安い順に並べた10案リスト、実配線前のスケッチ。

早い段階でやる理由：実装の途中で発覚した「未知の既知」は高くつく。仕様の小さな変更が実装の大幅な違いになり得るし、作りかけの巻き戻しは、別のスケッチを選び直すより難しい。

ユーザーに反応してもらい、その反応が明らかにしたこと——「密度の高いレイアウトを全部却下しましたね。つまり情報密度は本物の制約です」——を明示的な要件として記録する。

### インタビュー（既知の未知）

質問は**一度にひとつずつ**。アンケートにしない——各回答が次の質問を決めるからだ。最初の返答に含める必須の質問はちょうどひとつ：回答がアーキテクチャを最も左右する質問。現地を見せてもらう依頼は2つ目の質問には数えない——ただし、それが任意のショートカットであることが伝わる形にすること：「リポジトリを共有してもらえれば大半は自分で読み取ります。難しければ、まずこの質問だけ答えてください」。コードベースはユーザーが答えなくていい質問に答えてくれる。この道を差し出すコストはゼロで、しばしばインタビュー全体を置き換える。その質問がなぜ最初なのかを添えるのは良い（「これでキューが要るかどうかが決まります」）し、続く質問が何に依存するかを描いておくのも良い——だがまだ聞かないこと。そして記入式の仕様テンプレートを添付しないこと。テンプレートはインタビュー全体を宿題としてユーザーに手渡す行為であり、インタビューを機能させている核心——最初の回答のおかげで2つ目の質問が賢くなれること——を放棄してしまう。見た目に関する細部は最後か、聞かないまま終わってよい。残った曖昧さが作るものを変えなくなったら、そこで止める。

最後に、聞き取った内容を簡潔な仕様として復唱し、ユーザーに確認してもらう。

### リファレンス

ユーザーが欲しいものをうまく説明できないときは、実例がないか尋ねる——正しくやっているライブラリ、好きなデザイン、リポジトリ内の似た機能。ソースコードは圧倒的に最良のリファレンスだ。言語が違っても、スクリーンショットや説明文には載らない構造と意味を運んでくれる。リファレンスを読み、移植可能な本質を抽出し、どの性質が重要かをユーザーと確認する。

### 実装計画

計画は「徹底ぶりの証明」ではなく「論点の顕在化」のために書く。レビューで変わる可能性が高い部分——データモデルの変更、新しい型インターフェース、ユーザーに見えるものすべて——を先頭に置き、機械的なリファクタリングは末尾へ。計画の主役はレビューするユーザーだ。ユーザーの入力が意味を持つ場所に注意が向くよう並べること。

実装は新しいセッションで、計画とプロトタイプを成果物として渡して始めることを提案する。作り手はクリーンなコンテキストと、計画フェーズで掘り出したすべてを両方手にできる。

### 実装ノート（実装中）

どれだけ計画しても未知の未知は消えない。構築の途中でしか現れないものがある。作業中は `implementation-notes.md` を保持すること。エッジケースが計画からの逸脱を強いたら、保守的な選択肢を取り、「Deviations（逸脱）」見出しの下に理由とともに記録して、止まらずに進む。このノートが次の計画ラウンドの入力になる——こうしてユーザーの地図は少しずつ現地に近づいていく。

### ピッチ／説明資料（実装後）

レビュアーは、ユーザーがかつて持っていたのと同じ未知からスタートする。良いピッチ資料はその道筋をなぞり直す：まずデモか成果を見せ、次に下した判断と、潰しておいた失敗ポイント——専門家のレビュアーが突いてくる箇所——を示す。プロトタイプ・仕様・実装ノートをひとつの成果物にまとめ、ユーザーが Slack や PR の説明にそのまま貼れる形にする。

### クイズ（実装後）

長いセッションの後では、diff は変更の実態を過小に伝える。挙動は diff に映らない既存のコードパスに依存しているからだ。何をなぜ行ったかの文脈と直観が掴めるレポートを渡し、そのうえで変更内容のクイズを出す——トリビアではなく挙動に焦点を当てた、レビュアーが聞きそうな質問で。元記事が示す基準はユーザーにも繰り返し伝える価値がある：**合格するまでマージしないこと。**

## ガードレール

- **儀式の規模は賭け金に合わせる。** 1ファイルのバグ修正にインタビューは要らない。フルコースは、大きい・曖昧・不慣れな領域の作業のために取っておく。それ以外では、明確化の質問ひとつがパターンの全部でよいこともある。
- **実行するのは1つか2つのパターン。8つ全部ではない。** このフレームワークは診断ツールであって、チェックリストではない。
- **必ず、ユーザーがすぐ行動できる成果物で終える**：書き直したプロンプト、確認済みの仕様、計画、少数の決定事項。「あなたの未知はこれです」だけで「で、どうするか」がなければ、ユーザーは出発点に立ち尽くしたままだ。ただし成果物とは*いま*行動できるもののこと——何かが起きる前にユーザーが埋めねばならない空白のテンプレートは、成果物ではなく追加の宿題だ。テンプレートは、求められたときかインタビューが終わったときのために取っておく。
- **具体性のバランスを取る。** 失敗モードは対称的だ。指示が具体的すぎれば、Claude は悪い計画のまま崖から落ちるまで従う。曖昧すぎれば、ユーザーの実際の意図の代わりに一般的なベストプラクティスで埋める。ここにあるすべてのパターンの目的は、ユーザーの次のプロンプトをその両極の間に着地させることだ。
