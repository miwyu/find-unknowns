# ブラインドスポットパス（未知の未知）

件数・形式・停止条件・自己点検は、`SKILL.md` ステップ4の優先順位に従う既定値である。

ユーザーのタスクが実際に触れる範囲をコードベースやウェブで調査し、「聞くべきだと知らなかったこと」を教える。順位付きの発見と次の行動で依頼を明確にする。求められた報告書も適切な成果物である。

## 適用条件

- ユーザーが不慣れなドメイン、またはコードベースの不慣れな部分に入ろうとしている（「認証モジュールは触ったことがない」「カラーグレーディングが何か知らない」）。
- ユーザーが「ブラインドスポットパス」や「未知の未知」を名指しで求めた。
- まだ枠組みすら掴めていない事柄について、プロンプトの書き方を教えてほしいと言った。

- ソース・資料の調査や計測を要する事実が未確認である。希望する結果を聞くことと、実際の挙動を検証することを区別する。

リダイレクト：ユーザーが自分で質問に答えられるなら → インタビュー。欲しいものを見れば分かるタイプなら → ブレインストーム＆プロトタイプ。既存の実例を名指ししたなら → リファレンス探し。

## 入力

- ユーザーが述べたタスクと、すでに知っていること・試したことについて本人が語ったこと。
- コードベース（手元にあれば）——返信の前に読むこと。未知がリポジトリの知識ではなくドメイン知識であるときはウェブの情報源。

## 手順

1. ユーザーの出発点を、本人が語ったことから把握する。本当に不明なら、それについての短い質問ひとつを返信に織り込む——独立したラウンドにはしない。
2. 実質的なことを言う前に現地を調査する。コードベースなら：タスクが触れるモジュール、そのテスト、隣接機能、荷重のかかったコメント。ウェブなら：このドメインで「良い」とは何か、よくある失敗モード、専門家の語彙。
3. 未知の候補を4つの問いに照らして集める：ここにはどんな過去の作業があるか？「良い」とは何を指すか？ よくある落とし穴は？ 専門家なら聞くのにユーザーがまだ聞いていない質問は？
4. 「回答がどれだけ作るものを変えるか」で順位づけする。順位づけこそがあなたの付加価値だ——ユーザーにはまだ、荷重のかかる論点と些事の区別がつかない。
5. 初回ターンの契約に従って返信を書く：最小限に教え、重要な発見を通常3〜5個示し、網羅性を求められていなければ残りを保留する。

## 初回ターンの契約

返信には次を、この順で含める：

1. パターンの名乗りと、前提としているユーザーの出発点を1行で（「X についてブラインドスポットパスを実行しました——このコードベースにもレート制限にも初めてとのことなので、先にコードを読みました。現地はこう言っています」）。
2. **最大5文**のレクチャー：下の決定を理解するのに必要な最小限の文脈——百科事典の項目ではなく直観を。例外：ユーザーがコードベースを読んでほしいのではなく、ドメインを*教えてほしい*と求めた場合（「教えて」「プロンプトを書けるよう X を説明して」）は、提示する決定ごとに**最大2文**を、その決定の隣に足してよい——順位づけは維持、決定は最大5個のまま。
3. **発見を通常3〜5個。根拠を示し、確認済み事実、未検証の仮定、ユーザーの判断を区別すること。**「webhook のバーストをテナントのレート制限に含めるかどうかを決める必要があります」は「webhook があります」に勝る。
4. 残りを保留する1行：「細かいものもいくつかあります——見ますか？」（保留項目の名前を挙げるだけなら3〜5個の上限に数えない。説明したら数える。）
5. 発見を織り込んで元プロンプトを書き直す申し出——すでに求められていれば書き直したプロンプトそのもの。

頼まれていないテンプレートや網羅的な目録は出さない。調査には許可された小さな実験を含めてよいが、発見だけの依頼で製品の実装を始めない。

## 成果物

順位づけした発見と具体的な検証・判断の次の一手、および（申し出た、または届けた）書き直したプロンプト。その書き直したプロンプトこそ、ユーザーが次のパターンやセッションへ持ち込むものだ。

## 停止条件

- 求められた範囲を根拠で裏付けられ、追加調査が次の行動を変えにくくなったら止める。アクセス不足なら必要な証拠と検証方法を示す。件数だけでは調査を打ち切らない。
- 契約を届けたらターンを終える。実装を始めない。ユーザーの回答か、保留項目の選択を待つ。

## 良い例／悪い例

**良い例**（ユーザー：「レート制限を足したいけどこのミドルウェアは触ったことがない」）：

> レート制限まわりの現地にブラインドスポットパスをかけました——このミドルウェアにもレート制限にも初めてとのことなので、先にコードを読みました。聞くべきだと知らなかったことが3つあります：
>
> 1. **エンタープライズ契約の下限。** `auth.js` にエンタープライズ顧客へ「1000 req/min 以上」を約束するコメントがあります。決めること：制限はプラン対応の下限を持つテナント単位か、グローバルか？
> 2. **認証なしの webhook ルート。** `/webhooks/github` は認証を通らないため、ユーザーIDでキーイングすると静かに対象外になります。決めること：専用バケツを持たせるか？
> 3. **Redis のオフラインキューが無効。** Redis が瞬断すると呼び出しはキューに入らず例外を投げます。決めること：フェイルオープンかフェイルクローズドか？
>
> 細かいものもいくつかあります（テストの glob が壊れている、参照されている statsd が存在しない）——それも見ますか？ よければ、この3つの決定を織り込んだ形にプロンプトを書き直します。

**悪い例**（同じ依頼）：

> レート制限は大きなトピックです！ 考慮事項が14個あります：アルゴリズム（トークンバケット、スライディングウィンドウ、固定ウィンドウ…）、ストレージの選択肢、分散協調、HTTP 429 のセマンティクス、Retry-After ヘッダー、…… 先に進むため、この要件テンプレートを埋めてください：[20行の表]。

悪い例は、*この*コードベースを読む代わりに一般論のドメイン講義をし、順位づけのない目録を投げ、宿題を手渡している。

## 送信前の自己点検

- 現地（コードベース／ウェブ）を調査したか？ 一般的なドメイン知識を暗唱していないか？
- 各発見は根拠または明示した証拠不足に結びつき、事実・仮定・ユーザーの判断が区別されているか？
- 発見は求められた範囲で順位付けされているか（通常5個以下）。決定を捏造していないか？
- レクチャーは5文以内か（教えてほしいと求められた場合のみ、決定ごとに2文以内を追加）？
- 最初の行で、前提としているユーザーの出発点を述べたか？
- 書き直したプロンプトを申し出た（求められていれば届けた）か？
- 早すぎる製品実装と頼まれていないテンプレートを避け、未実施の計測を未検証と示したか？
