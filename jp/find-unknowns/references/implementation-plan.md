# 実装計画

件数・形式・停止条件・自己点検は、`SKILL.md` ステップ4の優先順位に従う既定値である。

計画は「徹底ぶりの証明」ではなく「決定の顕在化」のために書く。計画の主役はレビューするユーザーだ。ユーザーの入力が意味を持つ場所に注意が向くよう並べること——ユーザーは見えるものにしか拒否権を行使できない。

## 適用条件

- 発見フェーズが終わり（またはそもそも不要で）、要件は確定し、ユーザーはコードを書く前に決定を洗い出してほしい。
- ユーザーが計画、あるいは「始める前に何をレビューすべきか」を求めた。

リダイレクト：ユーザーにしか決められない重要な選択 → インタビュー。実証的な証拠の不足 → ブラインドスポットパス、または検証手順を含む条件付き計画。新しい証拠が前提を覆さない限り、確定済み要件を保持する。

## 入力

- 確認済みの仕様または述べられた要件と、以前のパターンの成果物（プロトタイプ、リファレンスの性質リスト、ブラインドスポットの発見）。
- 計画が触れるコード——計画を書く前に読むこと。すべての決定は、それが載る実際のファイルとインフラを名指しすべきだ。

## 手順

1. 計画が触れるコードを読み、各要件を実際にあるものと突き合わせる。現地とぶつかる要件（設定、契約コメント、存在しないファイル）は、黙った仮定ではなく決定項目になる。
2. 計画されたすべての作業を、**レビューでユーザーが変える可能性の高い順**に並べる：データモデルの変更、新しいインターフェース、ユーザーに見える挙動を先頭に。機械的なリファクタリングは末尾へ。
3. 上位の各項目に1行ずつ書く：何を選んだか、却下した代替案、なぜか。
4. 実装中にしか解けない未知を列挙し、作り手に実装ノートを保持するよう指示する（`assets/implementation-notes-template.md` を指す）。
5. 締めに、この計画（とプロトタイプ）を成果物として渡した**新しいセッション**での実装を提案する。

## 初回ターンの契約

計画文書そのもの（チャットに markdown、求められればファイル）を、既定ではこのセクション順で届ける：

1. **レビューしてほしい決定** — **3〜5項目**。各項目：何を選んだか／何を却下したか／なぜか。実際のコードに根ざしていること。
2. **順序** — 構築の順番。1ステップ1行。
3. **残存する既知の未知** — 構築中にしか現れないもの＋実装ノートの指示。
4. **機械的な作業** — **最大6行**に圧縮し、末尾に。手順の逐一指示ではなく成果として書く（「バリデーションヘルパーを抽出」）：ここは作り手を信頼する領域で、現地が計画と食い違ったときにピボットできる余地が要る。
5. 締めの1行：この計画を成果物として新セッションへ引き継ぐ提案。

確定済み要件を再質問せず計画を届ける。求められた計画ファイルの保存と短い例示は許される。計画だけの依頼では実装コードを書かない。

## 成果物

計画文書。ユーザーが1行ずつ拒否権を行使できる状態で。読み飛ばされそうなセクションは削る。

## 停止条件

- 計画だけの依頼なら届けたところで止まる。計画に続けて実装することも依頼されていれば、重要なユーザー判断が残っていない限り許可範囲で続ける。
- コードを読んで、アーキテクチャを変える曖昧さが見つかったら、ユーザーの選択と証拠のどちらが不足しているか見極める。必要な選択は聞き、それ以外は調査するか条件付きの計画と必要な検証を示す。

## 良い例／悪い例

**良い例**（将来設計の例示であり、返金フィクスチャの現状の説明ではない）：

> **レビューしてほしい決定**（あなたの目で変わる可能性が高い順）：
>
> 1. **新テーブル `refund_jobs`**。`payments` にステータス列を足す案ではなく——支払い行を不変に保てる。却下案：ステータス列方式。安いが監査クエリが汚れる。
> 2. **冪等性キーはクライアント支給ヘッダー**、必須。却下案：サーバー生成フォールバック——リトライのセマンティクスを静かに壊す。
> 3. **webhook 消費者に見せるのは `refund.settled` のみ**。中間状態は外に出さない。却下案：全状態ストリーム。誰も求めていない。
>
> 順序：マイグレーション → ジョブランナー → API → webhook。機械的作業：`validateAmount` ヘルパー抽出、死んだフラグ2本の除去（文書末尾）。

**悪い例**（計画の冒頭）：

> ## フェーズ1：準備
> 1.1 フィーチャーブランチを作成。 1.2 既存コードをレビュー。 1.3 テストフィクスチャを用意。
> ## フェーズ2：実装
> 2.1 モデルを更新… [時系列順の番号付きステップが40個続き、データモデルの決定はステップ2.3に「必要に応じてスキーマを更新」とだけ書かれて埋まっている]

悪い例は実行の時系列で並んでいるため、レビュー可能な決定がリストの中程に埋まり、選択ではなくタスクとして表現されている——そして「必要に応じてスキーマを更新」は、最もユーザーの目が必要だった決定を隠している。

## 送信前の自己点検

- 最初のセクションは「フェーズ1：セットアップ」ではなく、「Y ではなく X を選んだ」形式の項目3〜5個からなる「レビューしてほしい決定」か？
- すべての決定はコード内の実在するもの（ファイル、設定、契約）に根ざしているか——発明したインフラではないか？
- 機械的な作業は6行以内で、末尾にあり、手順の逐一指示ではなく成果として書かれているか？
- 残存する未知を明示し、実装ノートのテンプレートを指したか？
- 新セッションへの引き継ぎを提案したか？
- 確定済み要件の蒸し返しと、リポジトリへの実装コードの書き込みを避けたか？
