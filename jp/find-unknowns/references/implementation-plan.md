# 実装計画

件数・形式・停止・自己点検の既定値は `SKILL.md` ステップ4に従う。

レビューで変わりやすい決定を先に示し、既決要件を保った計画を実コードに基づいて書く。

## 適用条件

- 要件が固まり、実装前のレビューを求めた、または計画を依頼した。

ユーザーだけの重大な選択 → インタビュー。証拠不足 → ブラインドスポットまたは検証付き条件計画。

## 入力

- 確認済み要件と前段成果物。
- 触る全ファイル・基盤（作成前に読む）。

## 手順

1. 要件を実コードと照合し、衝突・欠落ファイル・契約コメントを仮定にせず決定事項にする。
2. 変更されやすい順（データモデル、境界、ユーザー挙動、機械的作業）に並べる。
3. 主な選択ごとに選択、却下案、根拠または推測したトレードオフを一行で書く。
4. 実装中に判明する未知と、assets/implementation-notes-template.md を使う指示を書く。
5. この計画とモックを添えた新規実装セッションを提案する。

## 初回ターンの契約

順序は「レビューする決定」3–5件、「順序」一行ずつ、「既知の残余未知」とノート指示、「機械的作業」6行以内（末尾）、「新規セッションへの引き継ぎ」。既決要件を再質問せず、計画だけならコードを書かない。

## 成果物

実ファイルに根ざし、一行ずつ却下できる計画。

## 停止条件

計画だけなら届けて停止。実装も依頼済みで重大な選択が残らなければ続行する。設計が欠けた選択に依存するなら質問し、それ以外は調査または条件付きで書く。

## 良い例／悪い例

良い：「payments を変更せず refund_jobs 表を追加（監査行を不変にする）；タイムスタンプ代替でなくクライアントキー必須（再試行安全）；migration → worker → API。」

悪い：「必要ならスキーマ更新」などの準備手順を大量に並べ、設計選択を隠す。

## 送信前の自己点検

- 最初にコード根拠の選択3–5件と却下案があるか。
- 残余未知とノート指示があるか。
- 機械的作業は末尾6行以内で成果表現か。
- 既決要件を保ち、計画だけで実装せず、引き継ぎを示したか。
