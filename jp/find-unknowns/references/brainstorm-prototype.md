# ブレインストーム＆プロトタイプ（未知の既知）

ユーザーが「反応することでしか自分の欲しいものを知れない」とき、反応する対象を生成する。目的は、本人が言語化できない好みと要件を——実装で高くつく前に、安く——表に出すことだ。実装の途中で発覚した「未知の既知」は手戻りを強いる。ここで発覚すれば、却下されたスケッチひとつ分のコストで済む。同じパターンは、スコープがまだ決まっていないセッションの入口にもなる：広く安い選択肢の一覧があれば、何かを作る前にユーザーが方向を選べる。

## 適用条件

- ユーザーが何らかの形で「見れば分かる」と言っている：ビジュアルデザイン、UX、命名、トーン、API の使い心地。
- 却下した試作はあるが理由を説明できない（「自分で作った3バージョンとも嫌だった」）。
- 大まかな問題や生煮えのアイデアがあり、コミットする前に選択肢の広がりを見たい（「介入できる場所をブレストして」「ここで何ができる？」）。

リダイレクト：ユーザーが既存の実例を**名指しした**（「X みたいに」）→ リファレンス探し。欲しいものについて質問に答えるだけで済むなら → インタビュー。「好みを言語化できない」と言ったユーザーに、前提条件としてそれを説明させないこと——それこそ本人が「できない」と伝えてきた唯一のことだ。

## 入力

- ユーザーの依頼と、すでに報告された却下済みの試作や反応。
- 問題になっている好みの次元（レイアウト？ 密度？ トーン？ アプローチ？）——不明なら、それがこのパターンで許される唯一の質問。候補と並べて、同じターンで聞く。
- どちらのモードか：**モックモード**（好み——レイアウト、トーン、使い心地。ユーザーには見るものが必要）か**リストモード**（スコープ——どこに介入するか、何を先に作るか。ユーザーには順位づけされたリストが必要）か。

## 手順

1. 候補が変化する次元を固定する。それ以外は一定に保ち、反応が好みだけを切り出すようにする。モックモードでの「一定」は数えられる形で：**同じ見出し、同じ機能説明文、同じCTA文言、同じダミーデータを、すべての候補に逐語で**——変えるのはレイアウト、タイポグラフィ、色、密度、順序だけ。変えたいのがコピーやトーンそのものなら、そう明言してレイアウトのほうを固定する。両方を同時に変えてはならない。
2. 本当に異なる方向性を作る——異なるレイアウト、メタファー、野心のレベルであって、ひとつのアイデアのバリエーションではない。バリエーションは、どうせ収束していた地点にユーザーの反応を浪費する。**モックモード：3〜5方向。リストモード：1行の候補を5〜10個、最も安いものから最も野心的なものへ順に並べる**。コードベースがあるなら各候補をそこで見つけた何かに結びつける（先に調べる）。
3. すべての候補を構造的に安く保つ：ハードコードしたダミーデータ入りの自己完結した単一HTMLファイル（モックモード）、または候補ごとに1行〜1段落（リストモード）。バックエンドなし、ビルドステップなし、実インテグレーションなし——それが必要な候補は、作らずに説明で済ませる。
4. ユーザーに反応を求める：選ぶ、却下する、混ぜる——一文で十分。
5. 反応が返ったら、それを明示的な要件に翻訳し（「密度の高いレイアウトを全部却下しましたね。つまり情報密度は本物の制約です」）、確認してもらう。この翻訳こそが成果物で、モックは足場だ。

## 初回ターンの契約

1. パターンの名乗りと、候補が何の次元で異なるのかを1行で。
2. 候補——モック3〜5個、またはリストモードなら安い順の1行候補5〜10個。それぞれに「何が違うのか」の1行説明——何のファイルも開かずに読める形で。
3. 締めの反応の問いかけひとつ：「どれが一番近いですか？ そしてそれの何が違いますか？」（任意で、添え物として：「気に入っている既存のページがあれば教えてください」。）
4. 抽象的な好みについての必須アンケートは無し。微調整用に提示される単一の「完成」ビルドも無し。

## 成果物

初回ターン：候補セット。反応後：明らかになった要件の確認可能なリスト。ユーザーにしか決められない決定が残っていれば**インタビュー**へ、そうでなければ実装計画へ渡す。

## 停止条件

- モックは5個、リスト候補は10個で生成をやめる。それ以上は反応を薄める。
- ユーザーの反応を要件として復唱し、確認できたらパターンを終える——そのうえでインタビュー（ユーザーにしか決められない決定が残っている場合）または計画へ引き継ぐ。パターンの途中でユーザーが既存の実例を名指ししたら、リファレンス探しへ切り替える。

## 良い例／悪い例

**良い例**（ユーザー：「このデータのダッシュボードが欲しいけど、視覚的センスが全然ない」）：

> ブレインストームの回です——密度と階層の異なる4方向、すべてダミーデータ入りの単一HTMLです：
>
> 1. **密なグリッド** — 全部見える、スプレッドシートの気配。
> 2. **一枚看板** — 数字ひとつ、他はワンクリック先。
> 3. **物語スクロール** — 読み順に並ぶチャートとキャプション。
> 4. **ターミナル** — 等幅、キーボード主体、装飾なし。
>
> `mockups.html` を開いて、どれが一番近いか・それの何が違うかを教えてください——却下も選択と同じくらい情報になります。

**良い例——リストモード**（ユーザー：「オンボーディング後にユーザーが離脱する。コードベースを調べて、介入できる場所を安い順から野心的な順にブレストして」）：

> ブレインストームの回です——介入できる場所を6つ、安い順に。それぞれリポジトリ内の何かに結びつけています：
>
> 1. **空状態の修正** — `Dashboard.tsx` は次の一手のない空のテーブルを描画している。半日。
> 2. **3日目のナッジメール** — メーラーにはテンプレートが既にある。トリガーをひとつ足すだけ。
> 3. **サンプルプロジェクトの露出** — `seed.ts` はあるのに、サインアップ後にどこからもリンクされていない。
> 4. **ダッシュボード上の進捗チェックリスト** — 新コンポーネント。既存フラグを読むだけ。
> 5. **アプリ内ツアー** — ライブラリとページごとのアンカーが必要。
> 6. **ガイド付きセットアップウィザード** — 新フロー、新しい状態、1週間ほど。
>
> どれが響きますか？ 外すものも挙げてください——却下は選択と同じくらいスコープを絞ります。

**悪い例**（同じ依頼）：

> サイドバー、チャートパネル4枚、設定ページ付きのダッシュボードを作って、あなたの API に配線しました。微調整があれば言ってください！

悪い例は、一般的ベストプラクティスで選んだひとつの方向にコミットし、形がユーザーの目に触れる前に実インフラを配線し、本当の未決事項が全体の形なのに細部への反応を招いている。

## 送信前の自己点検

- モック3〜5個（モックモード）または安い順の1行候補5〜10個（リストモード）で、それぞれバリエーションではなく本当に異なる方向か？
- モックモード：見出し・機能説明文・CTA文言・ダミーデータは候補間で逐語的に同一で、変わっているのは選んだ視覚的次元だけか？
- すべての候補はダミーデータで、実配線なし、ビルドステップなしか？
- ユーザーは一文で反応できるか？
- 抽象的な好みの質問を必須ステップにしていないか？
- 反応後：それを明示的で確認可能な要件として復唱したか——そしてユーザーにしか決められない決定が残っているなら、計画に直行せずインタビューへ渡したか？
