# Find Unknowns（未知の発見）

ユーザーの依頼と現実の制約の隔たりを解消し、本質でない選択は開いたままにする。枠組みの解説で終えず、適切な発見パターンを実行する。

## ステップ0 — 意図と範囲

どの段階でも、明示的な意図をルーティングの既定値より優先する。実装途中のブレストやマージ後の盲点調査も含め、名指しされたパターンや成果物を尊重する。パターンを指定せずスキルだけを呼んだ場合は、後続の既定分岐を使う。要約だけが求められたら要約を届け、クイズは提案にとどめる。

該当する明示依頼がなければ、定型作業や仕様が確定した作業に発見プロセスを足さず直接対応する。確定済みの決定と既存の承認を尊重する。前提を覆す新しい証拠があれば、その根拠を示し、影響する決定だけを再検討できる。調査や下書きの依頼から、実装・公開・送信の許可を推測しない。

## ステップ1 — 段階による既定分岐

ステップ0でパターンが決まっていない場合だけ使う：

- 完了した作業を他者へ説明したい → **ピッチ／説明資料**。ユーザー自身が理解を確かめたい → **クイズ**。
- このスキルの実行中に実装を進めている、またはユーザーや計画が逸脱記録を求めている → **実装ノート**。合意済み計画が存在するだけでは自動発動しない。
- 実装前、または影響するアプローチを再検討している → ステップ2。

## ステップ2 — いまの不確実性を解く

必要な情報に応じ、次の既定分岐を順に使う：

1. 欲しい結果を表す既存の実例が名指しされている → **リファレンス探し**。
2. 言語化できない好みや未確定のスコープがあり、反応するための案が必要 → **ブレインストーム＆プロトタイプ**。
3. 不慣れな領域、または調査・計測で確かめるべき事実 → **ブラインドスポットパス**。質問の前に得られる証拠を調べる。処理能力や実現可能性は、ユーザーに結果を推測させても解けない。許可範囲内の小さな検証を行うか、必要な代表的条件での計測を説明する。
4. 意図は固まり、ユーザーにしか決められない重要な選択が残る → **インタビュー**。
5. 要件が確定し、レビューできる計画が求められている → **実装計画**。

文脈から出発点を推定する。不足情報が次の有用な行動を変える場合だけ、焦点を絞った質問を一つ行う。選んだパターンと読み取った出発点を短く伝える。一度に一つのパターンを実行し、回答、新しい証拠、参照ファイルの引き継ぎでボトルネックが変わったら見直す。参照先のリダイレクトは既定値であり、明示依頼を覆す許可ではない。

## ステップ3 — 参照ファイルを読む

選んだ参照ファイルだけを読む。このスキル内の `references/` と `assets/` はすべて、この `SKILL.md` を含むディレクトリからの相対パスであり、作業リポジトリからのパスではない。読めない資料があれば制約を述べ、読み込んだと偽らない。

| パターン | ファイル |
|---|---|
| ブラインドスポットパス | `references/blind-spot-pass.md` |
| ブレインストーム＆プロトタイプ | `references/brainstorm-prototype.md` |
| インタビュー | `references/interview.md` |
| リファレンス探し | `references/reference-hunting.md` |
| 実装計画 | `references/implementation-plan.md` |
| 実装ノート | `references/implementation-notes.md` |
| ピッチ／説明資料 | `references/pitch-explainer.md` |
| クイズ | `references/quiz.md` |

各参照は8セクション：適用条件／入力／手順／初回ターンの契約／成果物／停止条件／良い例・悪い例／送信前の自己点検。実装ノートのテンプレートは開始用の素材であり、依頼された成果物の作成を制限するものではない。

## ステップ4 — 依頼の範囲内で実行する

以下は手順、出力契約、例、自己点検のすべてに適用する：

- **優先順位：** 利用環境の指示と権限の範囲で、ユーザー指定の範囲・形式・件数・継続・中止をスキルの既定値より優先する。それ以外はパターン別の契約、共通の既定値の順で適用する。停止条件は必要な入力を待つ依存作業の停止を意味し、独立して進められる許可済み作業は続ける。得ている承認を取り直さない。
- **確認質問：** 既定では1返信につき必須の確認質問は最大一つ。任意の文脈提供は追加の必須回答ではない。クイズの設問は依頼された成果物であり、確認質問ではない。複数の問いを一文に詰めて規則を回避しない。
- **件数：** 発見や決定は通常3〜5個を順位付きで示し、十分ならそれより少なくてよい。ブレストはモック3〜5個またはスコープ案5〜10個、リファレンスは性質3〜7個、クイズは4〜7問が既定。これらの成果物の件数は共通の5項目制限より優先する。補足説明や計画の作業手順を追加のユーザー判断として数えない。下限を満たすために項目を捏造しない。網羅的な調査や別の件数の明示指定を尊重する。
- **証拠：** 観測した事実、解釈、未検証の仮定、ユーザーの選択を区別し、実在するファイルや情報源を示す。ソースを読むだけでは性能測定や配備環境の挙動の証明にならない。必要なアクセスがなければ提供済みの証拠を使い、未検証事項と次の具体的な確認を示す。アクセスや結果を捏造しない。
- **利用能力：** 特定のツール名を必須にせず、使える機能で進める。質問UIがなければ通常の文章で聞く。書き込みや表示ができなければ使える文章やスケッチを渡し、未保存・未表示と明示する。作成・確認できなかった成果物を作った、見たと主張しない。
- **自律性：** 要件と承認を満たす選択肢の中で巻き戻しやすい変更を選び、逸脱を記録して続ける。巻き戻せるだけではアクセス制御や外部契約を弱める理由にならない。重要な未決のユーザー判断や不足する許可についてのみ確認し、依存やスキーマが関係するだけでは止まらない。
- **出力：** 行動できる発見、質問、候補群、計画、成果物、完了した作業を届ける。頼まれていないテンプレートや網羅チェックリストは出さない。言語と長さは読み手に合わせる。英語の語数制限を日本語へ機械的に適用しない。

## ステップ5 — 自己点検

選んだ参照ファイルの自己点検を、ステップ4の優先順位に従って適用する。解消できる不備は修正する。証拠やツールの不足で点検できないものは、合格を捏造せず制約と残る検証を示す。中止や方向変更の依頼を尊重する。

## 背景：4つの象限

- **既知の既知：** ユーザーが述べたこと。要件と現実に関する仮定を区別する。
- **既知の未知：** 自覚している空白。ユーザーの選択ならインタビュー、事実の不足なら調査・計測。
- **未知の既知：** 実例や試作に反応すれば分かる好み。
- **未知の未知：** 見落としていた問いや制約。ブラインドスポットパスで調べて教える。

同じタスクに4つすべてが含まれ得る。固定の段階ではなく、いまのボトルネックが次のパターンを決める。
